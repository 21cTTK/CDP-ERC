**MPU6050 陀螺仪集成**: ^b58764

本项目中仅使用 MPU6050 的**偏航轴角速度**（yaw rate）一个轴，也就是只用它检测水平方向上的转动角速度，以此判断小车运动方向的偏差。

本项目的实施是在速度环 PID 的基础上，利用偏航轴角速度做一个角速度环的 PID。它的输出是 **RPM** 的转速补偿，以**不累积**的方式叠加到速度环的设定值上（左右两轮反号），再由速度环输出 PWM 占空比。

### 协作式多任务系统

本项目采用了一种**协作式多任务**的设计，它能让我们简单地协调多个任务的进行，以达到同时运行多个并行任务的目的，它作为项目的底层架构影响了所有模块的设计方式。具体的概念可以拿这个关键词自行AI。

协作式多任务的思想有很多种实施方式，本项目选用的是其中某几种的结合，核心要素包括

- [[#^34c1de|阻塞与非阻塞]]
- [[#^736a0e|模块状态机]]
- [[#^3427e4|初始化和更新]]
- [[#^85e4e3|维护系统时基]]
- [[#^2cdeaa|状态机叠叠乐]]
- [[#^4f4fec|主循环速度]]

接下来我们以LED闪烁的状态机和蓝牙模块定时发送消息为例解释一下每个点的作用

___
**阻塞式LED闪烁**: ^34c1de

*阻塞与非阻塞*：

- **阻塞**：调用后原地等结果，等不到不返回。这段时间内 CPU 只服务这一个任务，主循环被卡在一个地方。
- **非阻塞**：调用只登记需求就立刻返回，接下来说的状态机的状态转移就是一个非阻塞式的操作（不含附带计算）

*阻塞式LED闪烁代码*：

> “豆包豆包，帮我写一个可以设定闪烁次数的LED闪烁代码”

```c
#include "stm32f10x.h"                  // Device header
#include "Delay.h"

#define LED_FLICKER_TIMES		67

int main(void)
{
	// Init
	//...
	
	// Main Loop
	while (1)
	{
		//...
		uint8_t times = LED_FLICKER_TIMES;
		
		while(times-- > 0)
		{
			GPIO_ResetBits(GPIOC, GPIO_Pin_13);
			Delay_ms(114);
			GPIO_SetBits(GPIOC, GPIO_Pin_13);
			Delay_ms(514);
		}
		
		//...
	}
}
```

*不足*：

- 单片机间歇式摸鱼 ${114},514$ 毫秒啥也不干
- 如果我们有 ${114514}$ 个可能需要同时闪的LED：
	- 定时任务直接被吞掉
	- 时间敏感的任务被持续延误
	- 多个延时叠加导致主循环过长，进一步延误其他任务

*结论*：主循环能触及到的代码中不能带这些

- `Delay` 函数: `Delay_ms(114);`
- 阻塞式循环: `while (times-- > 0);`
- 任何会长时间卡住主循环的东西

**初始化-更新模式**： ^3427e4

`CmtSys` 是一个状态机的集合，主循环调用一次 `CmtSys_Init` 把所有模块全部初始化（所有状态机进入初状态），再通过主循环不断更新每个模块（驱动每个状态机的转移）

```c
#include "stm32f10x.h"                  // Device header
#include "cmtSys.h"

int main(void) {
    CmtSys_Init();
    while (1) {
	    CmtSys_Update();
    }
}
```

**维护一个系统时基**： ^85e4e3

`g_SysMs` 的读数（准确来说是将其与各个模块内部的DDL变量比大小的的结果）作为系统中各个状态机进行状态转移的信号

![[Pasted image 20261022093347.png|555]]

*系统时基代码*：

```c
static volatile uint32_t g_SysMs;

void CmtSysTim_Init(void)
{
	// Set a TIM Counter to wrap around every 1ms...
}

void CmtSysTim_ISR(void)
{
	g_SysMs++;
}

uint32_t CmtSysTim_GetMs(void)
{
	return g_SysMs;
}
```

*每个模块的代码*:

假设我们需要蓝牙模块每隔 ${500}$ ms 回传一次数据，我们肯定不定硬等这么久（`Delay_ms(500)`），所以我们设计一个与时间相关的状态机

更新函数内：

```c
#include "CmtSys_TIM.h"
#include "HC05.h"

void CmtSys_Update()
{
    uint32_t     nowMs;                             //!< cmtSys_TIM module: provides system time
	
    nowMs = CmtSysTim_GetMs();
	
    if(HC05_PidMsgTimeReached(nowMs) != 0U)
    {
		//... whatever
    }
	
	//...
}
```

模块内：

```c
#define HC05_PID_MSG_INTVL_MS    500U

uint8_t HC05_PidMsgTimeReached(uint32_t nowMs)
{
	static uint32_t s_nextPidMsgMs;
	
	if(nowMs >= s_nextPidMsgMs)
	{
		s_nextPidMsgMs = nowMs + HC05_PID_MSG_INTVL_MS;
		return 1U;
	}
	return 0U;
}
```

每次主循环我们都把 *这一轮* 的实际时刻喂给各个模块的状态机，它们自己根据这个与时间相关的信号进行状态转移，完成各自的工作

___
**状态机叠叠乐**: ^2cdeaa

因为我们把每个模块或功能都当作实质上独立的状态机，它们内部的状态转移不受其他状态机的约束（不用硬等延时结束），我们理论上可以在这个更新函数（实质上的主循环）内叠加很多状态机。

*理想的主循环*：每次可以推动一堆状态机的状态转移

```c
#include "CmtSys_TIM.h"
#include "HC05.h"
#include "LED.h"
#include "Me.h"

void CmtSys_Update()
{
	uint32_t     nowMs;                             //!< cmtSys_TIM module: provides system time
	// other temporary variables
	
	nowMs = CmtSysTim_GetMs();
	// initialize those temporary variables
	
	// module 1
	if(HC05_PidMsgTimeReached(nowMs) != 0U)
	{
		//... whatever
	}
	
	// module 2
	if(LED_CheckFlicker(nowMs) != 0U)
	{
		//... whatever
	}
	
	// module 3  
	if(Me_DoSthUsefulTimeReached(nowMs) != 0U)
	{
		//... whatever whatever
	}
	
	// modules...
}
```

*模块间交互*：

- 由于每个状态机的状态和状态转移都是既定的，只有驱动状态转移的信号可能和外界交互，这就提供了一个良好的接口。
- 除了 `nowMs` 这个信号，每个模块肯定还要接受或修改其他模块信号，我们可以通过在主循环内部设计信号的交互方式来完成这个功能
- 每个系统的“小步”在状态机中独立执行，各个系统的状态转移在主循环中（几乎）同时推动，信号在主循环中交叉影响，构成一套完整系统。

说的比较假大空，我们可以看一个具体的例子

<u>示例</u>：蓝牙发送消息后LED闪烁

```c
#include "HC05.h"
#include "LED.h"

void CmtSys_Update()
{
    uint32_t     nowMs;
	
    nowMs = CmtSysTim_GetMs();
	
    //...
	
    if(HC05_PidMsgTimeReached(nowMs) != 0U)
    {
		LED_SetFlicker(nowMs, 3);
    }
}
```

*假设与实际*

要是每个状态机的每一次状态转移都是瞬时完成的就好了，但是实际上有些操作还是挺费时间的，比如通信和某些复杂计算，它们属于阻塞式操作，这就需要我们考虑下面的问题

___
**主循环速度**： ^4f4fec

要实现想上文设想的可以随意堆状态机的“理想主循环”，我们需要一个更新速度很快的主循环，如果主循环被某一个操作堵住，整个系统都会受影响。

<u>示例</u>：蓝牙发送消息缝合LED阻塞式闪烁

```c
#include "LED.h"
#include "HC05.h"
#include "Delay.h"

#define LED_FLICKER_TIMES		67

void CmtSys_Update()
{
	uint32_t     nowMs;
	uint8_t	 times = 0;
	
	nowMs = CmtSysTim_GetMs();
	
	//...
	
	if(HC05_PidMsgTimeReached(nowMs) != 0U)
	{
		times = LED_FLICKER_TIMES;
	}
	
	while(times-- > 0)
	{
		GPIO_ResetBits(GPIOC, GPIO_Pin_13);
		Delay_ms(114);
		GPIO_SetBits(GPIOC, GPIO_Pin_13);
		Delay_ms(514);
	}
}
```

如果 `HC05_PidMsgTimeReached` 内部的时间小于 LED 闪烁的总延时，下一次发送消息就会被延误一定时间。

*影响主循环速度的因素*：

- 首先，大多数信号交互都是简单的非阻塞赋值操作，影响不大
- 各个模块的单次状态转移通常很快，一般不会阻塞在一个地方；这一点要逐个模块评估

上面的例子说明系统容不得长时间阻塞。另一方面，一次非阻塞的状态转移内部往往仍带有大小不一的就地计算：多数很快完成，相当于没堵；但有些确实耗时很长。所以设计状态机时也要控制一次状态转移的实际耗时。

*设计技巧*：

- 与中断函数内代码的要求类似（“短平快”），一次状态转移需要有足够细的粒度
- 把需要大量计算的操作拆成几次完成（把一个状态拆成几个小状态），以自身操作变代价提升整体速度
- 如果协调得好，每个操作分割出来的“一小步”能很好地衔接，任务看着能并行运行
- 如果协调得不好，有些操作会一卡一卡的或看起来被放慢了

<u>示例</u>：OLED推送

用软件 I2C 给 OLED 发送数据，原本设定每 `X` 秒刷新一次屏幕，发现每当 OLED 刷新时，系统的主循环都会被延误很长一段时间，等待 OLED 完成刷新。

解决方法

- 原来一次推一页，现分成八次推
- 换成硬件I2C并选用最高速度
- 引入 DMA，不占用CPU资源搬运数据

*任务优先级*：

本项目的协作式多任务系统没有显式的优先级机制，主要就是要考虑到一次主循环肯定不能 *刚好* 落到你在每个模块内确定的时间间隔上，最大误差由主循环的最大时长决定，这个问题可以通过加快主循环解决（提升分辨率）

- 对于时间不敏感的：主循环时间轮询
- 对于时间敏感的：系统时基更新中断（示例：按键消抖，传感器采样）

### 编码器测速误差分析与实施

这一部分会分析在实际操作中：

- [[#测速原理|如何利用电机上的编码器测量车轮转速]]
- [[#误差分析|为什么不能用单一方法测速（误差分析）]]
- [[#测速方案|如何实施两个测速方法及它们之间的切换]]

我们先假装精确的速度测量和能在必要时切换测量方法是有用的，具体为什么有用留到后面 PID 的部分再解释。

#### 测速原理

**测频法和测周法**：

> **图片源**：江协科技STM32入门教程PPT课件

![[Pasted image 20260725213700.png|615]]

电机上的霍尔编码器会在轮子转动的时候产生脉冲，具体的频率由以下两个参数决定：

- **减速比**
- **线数**

我们使用定时器的输入捕获检测时候有边沿产生，并利用这些边沿来计算脉冲频率，进而得知轮子的转速。

其中具体的测量方法是：

- 测周法 - **TIM IC**
- 测频法 - **TIM Encoder Interface**

两种方法需要根据测得的转速交换使用。

#### 误差分析

**进行误差分析的动机**:

原本是只用编码器接口测量，结果发现反应到最终PID调控结果上抖动还是蛮大的，后面换成 IC 后可以缩到 $\pm1$ 的水平，但 IC 方法的局限有：

- 在速度高的时候理论上不如编码器接口
- 速度低的时候两个脉冲的间隔会超过设定的上限导致读不出数值

这两种情况下都需要切换成编码器接口测量，其中低速切换可以实测 IC 方法输出的非零最小值然后加一点余量设置为切换阈值，高速切换需要进行一定计算推导。

___
**变量定义**:

我们需要定义一些变量来进行分析。其中，电机的**转速**，**线数**和**减速比**是两种测量方法都用得到的变量，它们各自又有如下变量：

- 测频法（编码器接口）：倍频数；采样时间间隔
- 测周法（输入捕获）：定时器CNT自增一次的时间

于是，我们定义如下符号并在后面的分析中使用：

| 符号\[单位\]            | 何意味                  | 单位说明          |
| ------------------- | -------------------- | ------------- |
| $C_{\text{enc}}$    | 减速比 $\times$ 线数      | 与电机相关的常数      |
| $t\,[\mu s]$        | 定时器CNT自增一次的时间（tick值） | 以微秒为单位        |
| $m$                 | 倍频数                  | 与编码器接口配置相关的常数 |
| $\Delta t\,[\mu s]$ | 采样时间间隔               | 以微秒为单位        |
| $v\,[\text{RPM}]$   | 实际的车轮转速              | 以 $转/分钟$ 为单位  |

现在我们就能粗略估计误差系数，把它定义为一个可计算的函数了，具体见后文分析。

---
**测周法**:

*误差公式*：

测周法使用输入捕获捕捉两个相邻上升沿的时间测速（只计单通道上升沿，不倍频），误差系数可以由以下公式大致确定

$$\varepsilon_{\mathrm{IC}} \approx\frac{t}{T_{\mathrm{IC}}}$$

其中 $T_{\text{IC}}\;[\mu s]$ “两个相邻上升沿的时间；以微秒为单位” 为一个可以被表示为上表符号的中间变量。

*误差估计*：

注意到，$T_{\text{IC}}$ 可以表示为:

$$
T_{\mathrm{IC}}=\frac{60\times10^6}{C_{\mathrm{enc}}|v|} \quad [\mu s]
$$

代入上述公式得到：

$$
\boxed{\varepsilon_{\mathrm{IC}} \approx\frac{t}{T_{\mathrm{IC}}} =\frac{tC_{\mathrm{enc}}|v|}{60\times10^6}}
$$

从结果我们知道，以下几个变量和输入捕获测周法测量误差的大小正相关

- 速度 $v$
- 电机编码器的配置 $C_{\text{enc}}$
- CNT tick 值 $t$

___
**测频法**:

*误差公式*：

测频法使用编码器接口捕捉指定的脉冲边沿并使CNT自增或自减，我们每隔一段时间采样一次并归位，通过每次读到的CNT数来确定脉冲个数及方向，进而确定速度。其误差系数由以下公式大致确定

$$ 
\varepsilon_{\mathrm{Enc}} \approx\frac{1}{|\Delta C|}
$$

其中 $\Delta C$ “每次读到的CNT数” 为一个可以被表示为上表符号的中间变量。

*误差估计*：

注意到，$\Delta C$ 可以被表示为：

$$
\Delta C\approx \frac{C_{\mathrm{enc}}m|v|\Delta t}{60\times10^6}
$$

代入公式得到：

$$
\boxed{\varepsilon_{\mathrm{Enc}}\approx\frac{1}{|\Delta C|} =\frac{60\times10^6} {C_{\mathrm{enc}}m|v|\Delta t}}
$$

从结果我们知道，以下几个变量和编码器接口测频法测量误差的大小负相关

- 速度 $v$
- 电机编码器的配置 $C_{\text{enc}}$
- 采样时间间隔 $\Delta t$
- 倍频数 $m$

___
**误差比较**:

| 方法    | 误差公式 $\varepsilon$                                              | $v\uparrow$ 时 $\varepsilon$ 变化趋势         |
| ----- | --------------------------------------------------------------- | ---------------------------------------- |
| 输入捕获  | $\dfrac{tC_{\mathrm{enc}}\lvert v\rvert}{60\times10^6}$         | $$\varepsilon_{\mathrm{IC}}\uparrow$$    |
| 编码器接口 | $\dfrac{60\times10^6}{C_{\mathrm{enc}}m\lvert v\rvert\Delta t}$ | $$\varepsilon_{\mathrm{Enc}}\downarrow$$ |

以等号连接来计算高速交换的大致阈值

$$
\varepsilon_{\mathrm{IC}}=\varepsilon_{\mathrm{Enc}}
$$

把交换速度算出来是

$$
\boxed{ |v|_{\mathrm{cross}} =\frac{6.0\times10^7} {C_{\mathrm{enc}}\sqrt{m\,t\,\Delta t}} \quad[\mathrm{RPM}] }
$$

<u>示例</u>：

根据本项目的实际数据

- $C_{\text{enc}}=9.6\times11=105.6$
- $m=4$
- $t=1\;[\mu s]$
- $\Delta t=10\;[ms]=10^{4}\;[\mu s]$

按照规定的单位代入上述公式，我们可以算出速度阈值为：

$$ 
 |v|_{\mathrm{cross}} =\frac{6.0\times10^7} {105.6\sqrt{4\times1\times10^4}}\approx2840.91\;[\text{RPM}]
$$

也即

$$ \boxed{|v|_{\mathrm{cross}}\approx2.84\times10^3\;\mathrm{RPM}} $$

实际上我们的电机远远达不到这个速度，除了近乎静止的情况，**我们全部使用输入捕获测周法测速的结果即可**。

**输入捕获 - 回绕处理**: ^cce14e

项目中输入捕获与PWM共用一个 $\text{ARR}=1000 - 1$，即每 $1\text{ms}$ 就回绕一次的定时器，经常会遇到下一次测得的 CNT 值比上一次小的情况，不能简单作差计算时间间隔，我们需要启用这个定时器的更新中断来统计回绕次数以建立一个为测速服务的微秒级时钟来获取准确时间间隔。

```c
static volatile uint32_t g_WrapCount;

/// @warning return type `uint32_t` only lasts for ~71min counting time in us.
static uint32_t Enc_GetIcTimeUs(void)
{
	uint32_t wrap = 0;
	uint16_t cnt  = 0;

	do 
	{
		wrap  = g_WrapCount;
		cnt   = TIM3->CNT;
	} while(wrap != g_WrapCount);

	return (wrap * (uint32_t)ENC_IC_WRAP_US) + ((uint32_t)cnt * (uint32_t)ENC_IC_TICK_US);
}
```

*注意事项*：

输入捕获需要借助编码器确定**符号**

PID 的主要作用已经在前面的 [[#^176877|PID 闭环控制集成]] 和 [[#^b58764|MPU6050 陀螺仪集成]] 中简单说了，这里不再赘述。

#### 算法落地

**原理简述**:

PID 算法的具体内容可以在网上搜索资料学习，这里简单说一下大意

*大概地*：一种误差控制算法，闭环与开环

![[Pasted image 20261020134246.png|543]]

需要注意的是 PID 的理论是连续形式的

![329](https://bkimg.cdn.bcebos.com/formula/e662068384ee12d25d429c3c432fa4bc.svg)

真正落地时我们需要把公式离散化

*参数与公式*：

- $U_{k}$：第 $k$ 轮的输出
- $K_{p}$：比例系数
- $K_{i}$：积分系数
- $K_{d}$：微分系数
- $e_{k}$：第 $k$ 轮误差
- $\Delta e_{k}=e_{k}-e_{k-1}$：第 $k$ 轮误差与其上一轮误差之差

主要用到这个公式，与上面的连续形式对应

$$ 
U_{k}=K_{p}\cdot e_{k}+K_{i}\cdot \sum_{n=0}^{k}\,e_{n}+K_{d}\cdot\,\Delta e_{k}
$$

在电机调速场景下 $K_{d}$ 项的作用有限（编码器测速本身带有量化噪声，差分放大会把它放大成抖动），本项目中暂仅考虑 $K_{p}$ 及 $K_{i}$ 项。

___
**速度环**:

速度环 PID 函数的输入为 **实际速度** 和 **目标速度**，输出为 **PWM占空比**

$$ 
U_{\small \text{PWM}}=F_{\small \text{PID}}(v_{\small \text{目标}},\;v_{\small \text{实际}})
$$

只有速度环时，进行调控的流程是：

1. 通过蓝牙模块接收目标速度 $v_{\small目标}$
2. 待下一次编码器测速得到一个新实际值 $v_{\small 实际}$
3. 随之进行一次PID的更新
4. 调用电机模块的转速调节函数，传入PID的输出结果 $U_{\small\text{PWM}}$
5. 回到第二步

经过PID调控，实际值不断向目标值靠拢，实现可控速度

___
**角速度环**:

角速度环 PID 函数的输入为 **实际角速度** 和 **目标角速度**，输出为**转速补偿（RPM）**

$$ 
U_{\small \text{offset}}=F_{\small \text{PID}}(\omega_{\small \text{目标}},\;\omega_{\small \text{实际}})
$$

角速度环是在速度环的基础上做补偿，与速度环一起进行调控的流程是：

1. 通过蓝牙模块接收目标角速度 $\omega_{\small目标}$ 与目标速度 $v_{\small目标}$
2. 待下一次读取MPU6050得到一个新实际值 $\omega_{\small \text{实际}}$
3. 随之进行一次PID的更新，保存输出的 $U_{\small \text{offset}}$
4. 在下一次速度环PID更新前，保存原来的设定值 $v_{\small目标}$（`rampPoint`）
5. 将保存的 $U_{\small \text{offset}}$ 补偿到速度环的设定值上：左轮 $v_{\small目标}-U_{\small \text{offset}}$、右轮 $v_{\small目标}+U_{\small \text{offset}}$，记作 $v_{\small目标}'$（两轮同号叠加只是直行加速，不会转向）
6. 随之用 $v_{\small目标}'$ 进行一次PID的更新
7. 调用电机模块的转速调节函数，传入PID的输出结果 $U_{\small\text{PWM}}$
8. 把设定值还原为原来的 $v_{\small目标}$，让补偿不跨轮次累积
9. 进行下一轮

经过PID调控，实际角速度不断向目标值靠拢，实现可控转向，可用于让小车走直线

*$U_{\small \text{offset}}$ 为何不直接加到结果上*：

- 量纲不同：角速度环输出的是 **RPM**，速度环输出的是 **PWM 占空比**，两者不能直接相加
- 加到输出上就绕过了速度环的积分、限幅和缓启动，速度环的输出不再是“这一侧轮速”的唯一结果
- 不累积地叠加到设定值上，每一轮都是“基础设定值 $+$ 本轮补偿”，补偿不会一轮轮攒进速度环的状态，停车或切回直行时也不需要额外的清零逻辑

___
**实施细节**:

本项目原本只做了速度环PID，就把PID的处理和编码器测速模块缝到一起了，后面需要引入角速度环 PID 才把 PID 作为一个能被复用的模块独立出去，主要使用了一个结构体

```c
typedef struct __PID_PARAMS_STRUCT {
    float actual;
    float setPoint;
    float errorInt;
    float output;
    float rampPoint;
    /* Essentially Macros */
    float Kp;
    float Ki;
    float rampStep;
    float iTermClamp;
    float totalClamp;
} PidParams_t;
```

下面解释一些不在PID公式中的参数的作用

*缓启动梯度 - `rampPoint` 与 `rampStep`*：

实际上，要是我们在从静止到运动的第一轮PID迭代就直接把目标速度设定为给定的实际目标，从 $K_{p}\cdot e_{k}$ 算出来的输出就会非常大，一方面我们通过输出限幅 `totalClamp` 来防止输出超限（后面讲到），一方面我们设计一个缓启动梯度 `rampStep` 来从目标侧限制一轮PID最大能调整的目标值。

![[Pasted image 20261022165343.png|611]]

参数简述：

- `rampStep` 相当于一个宏定义，只在初始化中赋值，它决定梯度的大小
- `rampPoint` 存储本次的目标梯度，实质上替代了PID中的实际目标速度 $v_{\small目标}$ 作为每次更新的输入

*限幅机制 - `iTermClamp` 与 `totalClamp`*：

- 积分限幅 `iTermClamp`：防止积分项 $\displaystyle\,\sum_{n=0}^{k}\, e_{n}$ 越攒越多，导致后续“惯性”过大，无法矫正
- 输出限幅 `totalClamp`：输出当量与输入当量不同，需要根据限制可能输出的最值

*硬件实际*：

前面提到，我们只有两个驱动芯片，两侧各占一个驱动的输出，而速度环 PID 实际只能闭环控制每侧两个轮子中的一个，也就是实车上前轮为从动轮、后轮为主动轮。原因还是定时器不够用：STM32F103C8T6 只有 TIM1–TIM4 四个定时器，两路编码器接口占了 TIM1、TIM2，输入捕获与 PWM 共用 TIM3，1 ms 系统时基又占了 TIM4，没有多余的编码器接口给另外两个轮子做闭环。另外，每侧只有后轮（主动轮）装了编码器，转弯时前后轮的实际线速度并不相同，所以这里的“速度”指的是这一侧主动轮的转速。不过影响不大。

*MPU6050*：

实测发现静止时 MPU6050 偏航轴上的角速度读数并不为零，我们实际上需要设定一个经验参数 `MPU6050_GYRO_INIT_OFFSET_DPS` 来抵消这个误差。

___
**精度的考量**:

在做项目的过程中，我们深刻地意识到精度对PID效果的重要意义，PID要求**全过程的精度**，这意味着：

- 迭代窗口足够小：$50\mathrm{ms}\;\text{vs.}\;10\mathrm{ms}$
- 控制粒度足够细：PWM 频率
- 测速精度足够高：主要与数据波动相关
- 数据位数足够大：`float` 或扩大整数
- 需要控制各种与分辨率沾边的因素

PID调控的效果通常受限于上述因素中精度最差的那个。

*补充说明*：

这里的**迭代窗口**与**测速精度**与上文的[[#编码器测速误差分析与实施|编码器测速]]密切相关

**PWM 频率**对电机/驱动芯片的发热也会有影响，具体可以自行AI，结论是最好在 $2\text{-}15\text{kHz}$ 这个范围内

嵌入式开发的一大特点是软硬协同，单纯的软件正确不能保证最终功能可行，硬件相当于一个与软件对应的物理前端，它同样需要调试。有时候软硬件的交互会产生很多意想不到的bug，在做项目的过程中，写完一个功能但是效果不符预期，甚至是直接“无明显实验现象”是常态，为此，我们需要有一定的措施应对：

- 随做随测：做完一个功能就马上测试
- 递进开发：受限于硬件，很多时候不能很好地并行开发
- 版本管理：保留功能正常的软件版本，注意与硬件版本对应
- 安全增量：在验证可行的版本上开发，测试不成功的模块要硬件同软件一起回退，防止错误堆积或被之前的错误影响

*I2C 锁死*：

I2C 设备特有的问题，从设备有几率持续拉低SDA，发生时需要软件有特定流程恢复通信。

关键词 "**I2C Bus Clear**" 或 "**I2C 9-clock Recovery Routine**"，可以自行AI

```c
for (pulse = 0U; pulse < 9U; pulse++)
{
	HW_I2C_WRITE_SCL(0U);
	HW_I2C_WRITE_SCL(1U);
	
          if (HW_I2C_WaitSCLHigh() == HW_I2C_FAILURE) 
          {// SCL stuck low; set error and return with failure
              goto err;
          }
          // finish the routine once SDA is freed
	if (HW_I2C_READ_SDA != Bit_RESET) break;
}
```

**AI**:

开发过程中可以把AI的代码作为实施指导，学习代码中的编程技巧，或检查代码质量问题，但需要谨慎使用AI，下面是一些使用AI时需要考虑到的因素：

- **上下文输入**：各种智能体工具只能给AI软件部分的上下文，具体硬件连线的提示词输入极其考验使用者对自己做的东西的理解，硬件部分输入的不足经常会导致AI从代码猜测硬件也不说明假设，从而导致出bug的情况
- **代码形式**：AI写的代码一般都很专业、深奥、过抽象，经常把现阶段不必要的极端情况考虑进来
- **修bug的考量**：让AI修代码有几率会剧烈恶化上一点，有时为了修复一个小bug，AI会幻想一些极端误例或解决不存在的问题然后写进代码里；这常常是提示词写的有问题，或是让AI修AI写的代码，实际上AI挑人类写的代码毛病的能力确实很强。
- **修硬件bug的考量**：不能指望AI通过寥寥几句描述和人都看不懂的接线照片修硬件bug
- ~~开发人员的血压：用AI写代码会经常被气笑~~

在第三点中，AI还可能为了修复一个功能不择手段，影响其他正常模块的运行，不仔细审核每一行的改动会导致后续开发时之前正常的功能出问题，严重拖延工程时间。

### 检查清单

下面给出了我们总结的软硬件调试流程及注意事项

**硬件调试流程**：

当做出来某个功能没有按预期运行时：

*排查清单*：重点检查**供电**

- 检查**每个模块**都供上电了（留意连接问题）
- 检查**电池**剩余电量（电压是否下降）
- 检查整个系统的 **VCC/GND 一致性**。
- 检查具体那根**线**是不是真的导通。
- 检查具体那个**孔位**是不是好的（是否测不出电压）
- 用**示波器/万用表**看看波形是否符合预期（如果还有波形的话）

*其他注意事项*：

- 避开被占用的引脚和端口，比如 `PB3`
- 改了硬件配置后，记得同步改代码；保持硬件版本与软件版本的对应

<u>示例</u>: 一个由硬件版本与软件版本冲突导致的bug

软件版本

- **版本A**：PA6 为 GPIO 推挽输出，默认置高，用于LED；编码器接口测速用 PA0/1
- **版本B**：PA6 为 GPIO 上拉输入，用于输入捕获；编码器接口测速仍用 PA0/1

硬件版本：开发进行至**版本B**，把电机编码器输出并联接到 PA6

后续需要回退到版本A并行开发新功能，忘记回退硬件版本，这会导致并联的编码器接口测速的 PA0/${1}$ 被持续置高，无法接收脉冲

*典型症状*：

- **上不起电** $\dashrightarrow$ 有的 VCC/GND 引脚插反了，再折腾就要烧了
- **持续复位**：供电不足；电压跌到阈值以下，芯片自动复位。通常伴随一股大电流。检查**电压水平**——用示波器量电压是否稳定。

**软件调试流程**: ^b1baf6

1. 试着手动**复位**
2. 再确认**工程名**，确保你在正确的工程上
3. 检查常见的外设配置流程
	- **`Init()`**: 模块是否初始化
	- **`#include`**: 模块是否被加入
	- 是否 **RCC CLK** 使能，**APBx/AHB** 总线是否正确
	- 检查**外设编号**是否对应
	- 检查**引脚分配**（引脚和端口）对应
	- 是否改动过**硬件**
4. 全片擦除、重新编译、重新下载
5. 用**断点**来**调试**，定位具体问题。
	- 先保证**主循环**可以流畅运行：排查死循环或每一行的阻塞操作
	- 直接查看**寄存器**，查看值是否符合预期来检查是否是上述外设配置失误
	- 常见地在**中断服务函数**内部打断点检查是否是硬件问题无法触发中断
	- 在你寄予厚望的那一行上打断点来检查是否真的运行完这一行了
	- ...

### 调试技巧

这里列出了三个常用的调试小技巧来提高调试的效率

**利用LED**:

*工作指示灯*：

使用板载LED作为系统工作指示灯来检查主循环是否正常运行，还能顺带作为电压指示器

<u>示例</u>：

```c
#include "stm32f10x.h"                  // Device header
#include "cmtSys.h"

int main(void) {
	static uint8_t loopBlink = 0;

	CmtSys_Init();
	
    while (1) {
	/* --- BEGIN: Loop Indicator --- */
	if( (loopBlink++) % 2 )
		GPIO_SetBits(GPIOC, GPIO_Pin_13);
	else
		LED_TurnON(GPIOC, GPIO_Pin_13);
	/* --- END:   Loop Indicator --- */
		
		CmtSys_Update();
    }

	// Indicator for Loop breaked
	GPIO_SetBits(GPIOC, GPIO_Pin_13);
}
```

*初始化指示*：

在初始化时让工作指示灯闪烁，指示系统开始运行。可以用来检查系统是否异常复位

```c
for(int i = 0; i < 10; i++)
{
	LED_TurnON(LEDx);
	Delay_ms(50);
	LED_TurnOFF(LEDx);
	Delay_ms(50);
}
```

**全局变量调试**:

我们在调试的时候经常需要查看一些变量的值是否符合预期，而每个变量都只在运行到它所被定义的那个作用域中才能显示，否则就会是 `<cannot evaluate>`。一种方法就是打个断点在赋值处，然后停在那里看，但是太麻烦了，我们可以直接定义一个全局变量并将需要查看的变量赋给它，这样无需暂停就能看到变量的变化。
